# STORY-01-01-01 — Needs and places from inventory

**Status:** `todo` — **read this, then say go. Do not implement before that.**  
**Epic / feature:** EPIC-01 / FEAT-01-01  
**Suggested branch:** `story/STORY-01-01-01-inventory-places`

## What

The catalog API must answer two questions from **data**, not from a hard-coded south-India list:

1. What **needs** can we show? (from taxonomy that is actually used by at least one published programme, or from a maintained needs table — pick one rule and unit-test it.)
2. What **locations** can we show? Grouped the way you designed:
   - **State** as the group (KARNATAKA, KERALA, and later any other Indian state that has published retreats)
   - Under a state: **cities / areas** with a count, e.g. Bengaluru & nearby (5), Devanahalli (1)
   - A city appears only if at least one **published** retreat sits there (or the guest already selected it — same idea as “no zero-count unless selected”)

## Why

You overrode the spec: Healingram is India-wide **as soon as inventory exists**. Adding a retreat in another state must make that state appear without a code change to a state allow-list.

## What a guest should feel (PO)

They open location. They see only states we actually have. They pick Karnataka. They see that state’s cities and counts. They do not see a dead Goa row if we have no published Goa retreat.

## Acceptance

- `GET /api/catalog/needs` returns slugs/labels from Catalog (not a throwaway array in `CatalogModule` forever).
- `GET /api/catalog/places` (or equivalent, name it in Done) returns `{ state, cities: [{ id, label, count }] }` built from **published** retreats.
- Unit tests:
  - A published retreat in Tamil Nadu makes Tamil Nadu appear.
  - An unpublished retreat does not create a place.
  - Karnataka/Kerala are **not** special-cased in the query (no `if state in (karnataka, kerala)`).
- No frontend wiring required in **this** story (that is a later results story). Swagger or curl is enough for local UAT.

## Known leftover in code (do not “fix the world” here)

`PublicationGate` in Catalog still encodes the old spec geo. Removing that lock is **FEAT-01-02** (publication). This story only makes **needs** and **places** inventory-driven. If `PublicationGate` would make a Tamil Nadu test retreat invisible, seed/test data for this story must still be published under the current gate, or the places query must read location fields directly — say which you did in Done.

- Rewriting `PublicationGate` (next feature, unless it blocks the places test — then only the minimum)
